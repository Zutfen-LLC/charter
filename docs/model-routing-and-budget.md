# C05: Governed routing and accounting

## Serving boundary and configuration

`POST /v1/projects/{id}/model-calls` accepts `input`, `artifact_ids`, and an optional `model_id` (default `det-a`) and the existing `Idempotency-Key` header. `model_id` is a registry key, never a provider model override. Unknown body fields and trailing JSON values are rejected. Request identity binds the caller, project, input, source selection and explicit model key; omitted keys preserve the historical fingerprint. Completed retries are delivery-only and require fresh authorization. The API does not accept a credential, URL, destination class, transport or fallback preference.

The compiled registry in `internal/routing` is server-owned and immutable for a running process. Project policy is a separate, explicit allowlist committed in PostgreSQL. There is no access without a current policy. The pilot contains two in-process deterministic adapters, `det-a` and `det-b`; `hosted-test` describes a disabled hosted class and has no transport. `local-http` is disabled without an explicit `CHARTER_LOCAL_MODEL_URL`. It requires a literal HTTP loopback URL, has no DNS lookup, ambient proxy or redirects, and cannot fall back. Its endpoint ID is derived from the exact configured URL. Never configure a loopback forwarder, proxy, or other relay to an external provider. The retained synthetic serving profile permits **only in-process** adapters and refuses configuration of a model HTTP endpoint. That profile does not gain any external egress or production authority from C05.

The local adapter posts the exact sealed Charter JSON request (`model`, `input`, `excerpts`) once, with a bounded response/deadline. It does not implement an OpenAI-compatible API. A conforming endpoint responds with `{"output":"...","usage":{"input_bytes":123,"output_bytes":3}}`; the counts must match the bytes observed by Charter. A trusted endpoint may explicitly refuse billable inference with HTTP 422 and `{"rejected":true,"billable":false}`; this confirms receipt of the bytes, not successful inference or delivery. Other HTTP failures, malformed or missing usage, and unconfirmed acceptance are not proof of zero charge. No hosted or live model is needed to exercise the protocol. Any real-model smoke requires independent approval of the exact endpoint and test environment.

Provision the distinct `charter_budget_app` login using `scripts/provision-runtime-roles.sql` with `budget_user` and `budget_password`, then set `CHARTER_BUDGET_DATABASE_URL` for authenticated serving. It must address the same coordination database and schema; the retained profile pins it to the signed C04 authority. The workspace and evidence logins cannot read or write ledger tables or execute their transition functions. The budget login has narrowly scoped transition authority and no content access or policy administration. The login and its credential belong to the serving process only. An offline, trusted owner provisions pilot routing policy with the `evidence_budget_set_policy` SQL function after migration (tenant UUID, project UUID, local-only boolean, allowlist `text[]`, project cap, optional tenant cap). No public policy mutation endpoint is available in this slice. Ordinary app roles cannot remove configured projects to bypass a ledger obligation.

## Accounting and two durability domains

A unit is an integer cost unit, not a floating-point currency amount or estimated token count. The pilot rates are one unit per submitted request byte and one per output byte. The reservation covers the exact serialized request size plus the adapter's enforceable response-output byte limit. Registry and verifier amounts are bounded to the interoperable canonical integer range. The ledger uses UTC days at reservation time, an explicit project cap, and the lowest applicable non-null tenant cap across project policies. Open claims from earlier days still count against new admissions; terminal accounting stays attributed to its original reservation day. `usage_reserved` identifies the governed accounting version and registry model. An acknowledged output record can carry exact provider cost. `usage_settled` uses the existing `provider_reported` and `reserved_max` bases; a pre-dispatch refusal can explicitly prove zero billable work without changing C04's conservative disclosure classification.

| Window | On refusal or restart |
| --- | --- |
| Admission before claim, claim write unconfirmed, or claim before durable disclosure intent | No provider call. If a claim exists and was never armed, release it only after a verified terminal turn. |
| Durable intent before/at dispatch marker | The marker is committed in PostgreSQL before any invocation. An ambiguous marker response never authorizes a call. If the durable marker is armed and no exact evidence exists, charge conservatively. |
| Armed before last policy/authorization checks | Re-read route, member and ownership state. Proven refusals can settle zero; crashes without that proof are unknown. |
| Provider receipt, partial output, timeout, cancellation, evidence loss | With no verified exact cost, keep the claim or settle conservatively. Never redispatch. An acknowledged exact cost is used even if output delivery later fails. |
| Terminal retained evidence before PostgreSQL settlement | Replay verifies the installed evidence backend and applies idempotent reconciliation if necessary; it cannot resend or incur a second charge. |

A trustworthy measured overrun is recorded at its full amount, freezes admissions in scope and is not represented as cap preservation. When the result is observed but its evidence cannot be committed, a separately persisted overrun floor preserves that coordination obligation. If both the observation and its recording are lost, neither store can reconstruct that unobserved fact. The baseline unknown charge is the maximum reservation; ambiguous overrun exposure is not evidence that the provider respected the cap.

The mutable ledger is not the authority for retained output or evidence. With retained storage, reserve, arm, and settle are PostgreSQL operations and evidence acknowledgments are exact-version signed storage operations; there is no cross-store transaction. Recovery runs before serving behind C04's paired owner/drain locks, never invokes a provider, and leaves unverified obligations outstanding. Offline verification can reconstruct retained request, governed costs recorded in evidence, output and release authorization without PostgreSQL; it cannot infer successful client delivery, transient observations never retained, or recreate coordination identity, caps and pending holds. Loss or replacement of the retained coordination database does **not** permit in-place rebind: quarantine the old deployment, verify the original storage independently, reconcile obligations with the operator, and qualify a distinct deployment before accepting new work. The PostgreSQL-only development profile is not retention-enforced.

## Operator visibility and qualification

`GET /v1/projects/{id}/usage` requires an enabled user with both the tenant operator role and explicit project membership; authorization is fresh at entry and before response. It shows UTC period, configured cap, outstanding/actual/conservative cost units, per-model totals and available project capacity. It contains no content, provider request/response body, headers, credential or URL. Operator status does not grant implicit content membership or alter role separation.

Run `scripts/dev.sh test` against disposable PostgreSQL, `go test -race -count=1 ./...` with the same test DSN, `go test -count=10 ./internal/evidence ./internal/server -run '^TestC05'`, and `python3 -m unittest discover -s tests/contracts`. The pinned C04 procedure in [retention-qualification.md](retention-qualification.md) drives the synthetic retained service, exact version readback, and the C03/C04 fault cases. No paid provider, live endpoint, production deployment, arbitrary egress, or multi-instance serving is qualified by these tests.
