# Serving ownership and handoff

Charter requires direct PostgreSQL sessions, or a proxy that preserves session identity and advisory locks. Transaction-mode pooling, transparent session replay, multiple independently writable PostgreSQL primaries, and mixed deployments with old binaries that don't take the drain lock are unsupported. Stop the old deployment before starting this version.

Startup takes the existing schema-scoped ownership lock and a second schema-scoped drain lock on distinct dedicated connections. Both are mandatory; there is no reacquisition during a process lifetime. Startup recovery scans and writes using the exact PostgreSQL session holding the ownership lock, completes before HTTP starts, and has no host-clock cutoff. Admissions, object writes and evidence appends commit on that same session. They cannot silently hop to a new session after a disconnect. Acquiring both locks on a replacement is a prerequisite to its scanning or writing recovery records. If either one connection fails, a surviving lock prevents a successor from recovering while the old instance stops and drains.

The idle monitor makes lock-session failure a fatal serving transition. It is not the synchronization primitive: in addition to doing write transactions on the owner session, the recorder checks both physical connections synchronously before admission, dispatch and final delivery. The HTTP adapter checks again before writing model output. Failure is latched; the listener stops accepting connections and request contexts are cancelled. The owner releases its remaining locks only after all handlers exit, including on graceful shutdown. A stuck adapter can delay drain indefinitely; an operator can terminate the process, rather than instructing it to release ownership while it still runs. The owner session serializes evidence transactions, which limits write concurrency by design.

After a database restart or cluster/network failure that breaks both sessions, PostgreSQL releases both locks and can admit a replacement once reachable. Old-session admission and evidence appends cannot commit on the replacement database session, and old requests paused upstream of a fresh check cannot cross it. Recovery never redispatches. If intent was acknowledged and provider acceptance was not durably recorded, recovery preserves unknown disclosure and the reserved-maximum settlement. Already dispatched bytes cannot be recalled. A check and a write to a remote provider/client aren't one atomic operation: loss of both sessions in the interval after a synchronous check, or bytes already queued for transport, cannot be revoked. An unrestricted remote transport cannot provide exactly-once physical dispatch or delivery across that interval. A real provider adapter must honor request cancellation and would need receiver-side fencing/idempotency to claim stronger guarantees. This slice dispatches only to its synthetic stub.
